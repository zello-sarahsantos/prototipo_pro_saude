Chegou a ser removido nesta mesma rodada por parecer redundante com a nova aba, mas o usuário pediu explicitamente para mantê-lo também na tela de Início "assim como já estava" — restaurado com o mesmo comportamento (`isNovo` em `ServidorLayout.tsx`). ## 2. Correção de contraste — botão "Enviar Comprovante" (status "Requer Atenção")
- **Arquivo:** `src/routes/servidor.dependentes.tsx`.
- **Bug:** o botão usava a classe `text-warning-foreground` — cor quase branca (`oklch(0.99 0 0)` em `src/styles.css`), pensada para texto sobre um fundo `bg-warning` **sólido** — só que o botão usa fundo `bg-warning/10` (quase transparente). Resultado: texto praticamente invisível (branco quase sobre branco).
- **Correção:** trocado para `text-warning` (a cor âmbar em si) + `font-medium`, o mesmo padrão já usado em outros pontos do app para a combinação "fundo claro + borda + texto" sobre `bg-warning/10` ou `/5` (ex: `admin.comprovantes.tsx:436`, `routes/index.tsx:26`). Nenhuma outra ocorrência de `text-warning-foreground` sobre fundo claro foi encontrada no restante do código.

## 3. Requerimento de Primeira Inclusão — identificação de plano "Empresarial"
- **Tela/fluxo:** `src/routes/primeiro-acesso.tsx` (Primeiro Acesso → "Solicitação inicial de inclusão no Pró-Saúde"), passo "Plano".
- **Campo novo:** `empresarial: boolean` no estado local `plano` (default `false`), controlado por um componente `Switch` com rótulo dinâmico "Sim"/"Não", posicionado junto aos campos Operadora/Modalidade/Administradora (grid próprio, abaixo deles).
- **Aviso condicional (sem necessidade de salvar):** quando `plano.empresarial` é `true`, aparece imediatamente um bloco (`bg-amber-50 border-amber-200`, ícone `Info`) com o texto exato: *"Planos empresariais exigem o envio da fatura técnica no momento do envio de comprovantes de pagamento, pois o boleto empresarial isolado não permite identificar os valores individuais dos beneficiários."*
- **Persistência:** `handleSubmit()` grava `plano.empresarial` dentro de `TitularCadastroPlano.empresarial` via `saveTitularCadastro()` (chave `prosaude_titular_cadastro`, `src/lib/prosaude-storage.ts`). O campo `empresarial: boolean` já existia no tipo `TitularCadastroPlano` antes desta mudança, mas não era exposto nem preenchido pela UI.
- **Relação com o Módulo de Pagamento — requisito de produto, não só nota de integração:** este campo é o dado de cadastro real que **deveria** determinar, no sistema de produção, se o usuário vê o fluxo de Fatura Técnica (empresarial) ou o fluxo de Boleto/Recibo/Demonstrativo (individual/familiar) no Módulo de Pagamento (ver `docs/MODULO_PAGAMENTO.md`, seções 6 e 3.17). **Hoje os dois não estão conectados** — o Módulo de Pagamento, por ser só um protótipo sem cadastro real integrado, usa mecanismos de teste (um toggle manual em `localStorage` e uma convenção de nome de arquivo) para simular os dois perfis, e **não lê** `prosaude_titular_cadastro.plano.empresarial`. Isso é aceitável no protótipo, mas **no sistema real esse mecanismo de teste não deve existir**: o tipo de plano precisa vir sempre do cadastro (este campo), de forma automática e não controlável pelo usuário final, e o tipo de cada documento anexado precisa ser reconhecido por OCR/IA real a partir do conteúdo do arquivo — nunca do nome do arquivo. Ligar os dois é o próximo passo de maior prioridade registrado no documento do Módulo de Pagamento (seção 14).
- **Regras respeitadas:** nenhum documento adicional passou a ser exigido no cadastro (o aviso é só informativo); não houve alteração de obrigatoriedade/validação dos demais campos do passo "Plano"; nenhuma tela nova foi criada.
- **Arquivos principais:** `src/routes/primeiro-acesso.tsx` (campo + aviso + gravação); `src/lib/prosaude-storage.ts` (`TitularCadastroPlano.empresarial`, já existente, agora efetivamente usado).
- **Status de commit:** já implementado e commitado em sessão/commit anterior (`61ba3a6 — Atualiza fluxo de primeiro acesso do Pró-Saúde`), antes do início do Módulo de Pagamento. Esta seção documenta retroativamente esse comportamento, que não havia sido registrado até agora.

## 4. Requerimento de Mudança de Plano — incluir novo(s) dependente(s) no mesmo requerimento
- **Tela/fluxo:** `src/routes/servidor.requerimento.novo-plano.tsx`, passo "Dependentes" (função `StepDependentes`).
- **Reuso do formulário de Inclusão de Dependente:** o formulário completo de 4 etapas (Dependente, Plano, Documentos, Revisão — com as mesmas validações de CPF/campos obrigatórios/regra de idade/tipo de laudo, e a mesma matriz `DOCUMENTOS_POR_TIPO_DEPENDENTE` renderizada via `DocumentosDependenteUploads`) foi extraído para um componente compartilhado `IncluirDependenteForm` (`src/components/IncluirDependenteForm.tsx`), com props `submitLabel?: string` e `onSubmit: (value: IncluirDependenteValue) => void`.
  - A tela original `src/routes/servidor.requerimento.incluir-dependente.tsx` agora é apenas um wrapper fino em torno desse componente (`<IncluirDependenteForm onSubmit={() => setDone(true)} />`) — nenhuma lógica de formulário duplicada.
- **Botão "+ Incluir dependente"** abaixo da lista de dependentes já cadastrados, dentro de `StepDependentes`. Cada clique adiciona um novo bloco (`{ id: string; saved: boolean; value?: IncluirDependenteValue }`) ao estado `newDependentBlocks` — múltiplos blocos são suportados (repetir o botão).
- **Renderização de cada bloco:**
  - Enquanto `!b.saved`: renderiza `<IncluirDependenteForm submitLabel="Adicionar dependente" onSubmit={...} />` **inline**, dentro da própria tela (sem modal, sem navegação).
  - Depois de confirmado (`b.saved === true`): vira um card somente-leitura com resumo (Nome, Tipo, Plano, quantidade de documentos anexados).
  - Cada bloco tem um botão de remover (ícone `X` no cabeçalho) que tira o bloco inteiro de `newDependentBlocks` — funciona tanto antes quanto depois de salvo.
- **Trava de envio:** o botão final do wizard ("Enviar para análise da GERDAB") fica **desabilitado** enquanto `hasPendingNewDependents = newDependentBlocks.some(b => !b.saved)` for verdadeiro — o servidor precisa concluir ("Adicionar dependente") ou remover cada bloco aberto antes de conseguir enviar o requerimento inteiro.
- **Dependentes já cadastrados não são afetados:** eles continuam tratados por uma estrutura totalmente separada (`dependentsData`, com ações manter/alterar/remover por dependente já `ativo`) — os novos blocos não interferem nela, e nenhuma documentação é solicitada de novo para quem já está cadastrado.
- **Persistência:** `handleSubmit()` grava `novosDependentes: newDependentBlocks.filter(b => b.saved && b.value).map(b => b.value)` (um array de `IncluirDependenteValue`) dentro de `RequerimentoMudancaPlanoDraft`, junto com `newPlanData` e `dependentsData`, via `saveRequerimentoMudancaPlano()` (chave `prosaude_requerimento_mudanca_plano`, `src/lib/prosaude-storage.ts`) — ou seja, os novos dependentes são gravados como parte do **mesmo envio/rascunho** do requerimento de mudança de plano, não como registros separados.
- **Regras respeitadas:** não altera o fluxo existente de migração/remoção de dependentes já cadastrados; reaproveita 100% do formulário e das validações da Inclusão de Dependente (não recriado do zero); nenhuma tela nova foi criada — tudo ocorre dentro do wizard já existente de Mudança de Plano.
- **Arquivos principais:** `src/routes/servidor.requerimento.novo-plano.tsx` (botão + blocos inline + envio conjunto); `src/components/IncluirDependenteForm.tsx` (formulário extraído e reutilizado); `src/routes/servidor.requerimento.incluir-dependente.tsx` (tela original, agora wrapper fino do mesmo componente); `src/lib/prosaude-storage.ts` (storage compartilhado).
- **Status de commit:** já implementado e commitado em sessão/commit anterior (`ae5d702 — Permite inclusao de dependente no requerimento de mudança de plano`), antes do início do Módulo de Pagamento. Esta seção documenta retroativamente esse comportamento, que não havia sido registrado até agora.

## 5. Requerimento de Mudança de Plano — identificação de plano "Empresarial" no novo plano
- **Tela/fluxo:** `src/routes/servidor.requerimento.novo-plano.tsx`, passo "Novo Plano" (função `StepNovoPlano`, etapa 3 de 6 do wizard).
- **Motivação:** o usuário pediu que este requerimento refletisse o mesmo campo já existente no Requerimento de Primeira Inclusão (seção 3) — quando o servidor está solicitando mudança para um plano diferente, o sistema precisa saber se o **novo** plano é empresarial, pelas mesmas razões (regra de fatura técnica no Módulo de Pagamento).
- **Campo novo:** `empresarial: boolean` adicionado ao estado `newPlanData` (default `false`), reaproveitando exatamente o mesmo componente e o mesmo texto já usados no Primeiro Acesso — `Switch` com rótulo "Sim"/"Não", posicionado logo após "Modalidade do novo plano" (antes de "Valor individual do novo plano").
- **Aviso condicional idêntico ao da seção 3:** quando `newPlanData.empresarial` é `true`, aparece o mesmo bloco `bg-amber-50 border-amber-200` com o texto: *"Planos empresariais exigem o envio da fatura técnica no momento do envio de comprovantes de pagamento, pois o boleto empresarial isolado não permite identificar os valores individuais dos beneficiários."*
- **Exibido também na Revisão (etapa 6):** o valor ("Sim"/"Não") aparece na lista de dados do novo plano, junto de Nova operadora/Nova administradora/Modalidade/Valor individual.
- **Persistência:** como o restante de `newPlanData`, é gravado dentro de `RequerimentoMudancaPlanoDraft.newPlanData` via `saveRequerimentoMudancaPlano()` (chave `prosaude_requerimento_mudanca_plano`) — **não** escreve em `prosaude_titular_cadastro` (que é o cadastro "oficial" atual, escrito só no Primeiro Acesso). Isso é intencional: um requerimento de mudança de plano é uma **solicitação pendente de análise da GERDAB** (status "Em Análise"), não uma alteração imediata do cadastro — mesma lógica já aplicada aos demais campos deste wizard (nenhum deles atualiza o cadastro atual diretamente; tudo fica no rascunho do requerimento até uma eventual aprovação, que este protótipo não simula).
- **Relação com o Módulo de Pagamento — mesma ressalva da seção 3:** este campo também é, por enquanto, apenas capturado — não há conexão automática com `getTipoPlanoPagamento()`/`tiposDocumentoPorPlano` no Módulo de Pagamento. A integração real (cadastro → regras de fatura técnica) permanece como o próximo passo de maior prioridade (ver `docs/MODULO_PAGAMENTO.md`, seção 14, item 1) — que agora precisa considerar **duas fontes** de verdade sobre o tipo de plano (`prosaude_titular_cadastro.plano.empresarial`, do cadastro atual, e `prosaude_requerimento_mudanca_plano.newPlanData.empresarial`, de uma mudança pendente) e decidir explicitamente qual prevalece enquanto o requerimento de mudança não é aprovado.
- **Regras respeitadas:** nenhuma validação de obrigatoriedade foi adicionada para este campo (é informativo, como no Primeiro Acesso); não foi criada nenhuma tela nova; nenhum outro passo do wizard de Mudança de Plano foi alterado.
- **Arquivos principais:** `src/routes/servidor.requerimento.novo-plano.tsx` (campo + aviso + exibição na revisão); `src/lib/prosaude-storage.ts` (`RequerimentoMudancaPlanoDraft.newPlanData`, tipo genérico `Record<string, unknown>`, já acomodava o campo sem alteração de tipo).

## 6. Modalidade do plano do dependente — campo estruturado (Individual/Familiar × Empresarial)

- **Contexto:** ajuste pontual pedido pelo usuário junto com o fechamento da Etapa 7 do Módulo de Pagamento (ver `docs/MODULO_PAGAMENTO.md`, seção 3.25) — mas o próprio campo mexido é do módulo de Requerimentos, por isso documentado aqui, não lá.
- **Pedido:** nos fluxos que permitem incluir um dependente com plano **diferente** do titular, perguntar explicitamente se a modalidade desse plano é Empresarial — e nunca herdar esse dado automaticamente do titular, já que titular e dependente podem ter operadoras, modalidades e vínculos de associação diferentes entre si.
- **Campo já existia como texto livre — evitada a duplicação com um booleano `empresarial`:** os 2 pontos afetados já tinham um campo "Modalidade/tipo do plano" (`<input>` de texto livre, placeholder "Ex: Coletivo Empresarial") quando o plano do dependente é diferente do titular. Em vez de manter esse texto livre **e** adicionar um booleano `empresarial` separado (como existe para o plano do **titular**, seção 5 — ver ressalva abaixo), o campo existente foi convertido para um único `<select>` estruturado com 2 opções: "Individual/Familiar" e "Empresarial".
- **Vocabulário compartilhado com o Módulo de Pagamento, sem misturar dados dos 2 módulos:** o novo tipo `ModalidadePlano = 'empresarial' | 'individual_familiar'` e o mapa de rótulos `modalidadePlanoLabels` (`src/lib/mock-data.ts`) já existiam e já eram usados por `BeneficiarioPagamento.modalidadePlano` no Módulo de Pagamento (Etapa 2, Carlos/Marina/Pedro) — passaram a ser reaproveitados também pelo módulo de Requerimentos (João/Ana da Silva). O tipo/rótulo é compartilhado; os **dados** de cada cenário continuam isolados como sempre (ver seção 3 deste documento) — só o vocabulário é comum, para que uma futura integração real entre os 2 módulos não precise traduzir valores.
- **2 pontos alterados:**
  - `src/components/IncluirDependenteForm.tsx` — `IncluirDependentePlano.modalidade` (antes `string`) virou `ModalidadePlano | ""`; o `<input>` de texto livre no passo "Plano" (quando `mesmoPlano === "nao"`) virou `<select>`; a validação do passo (`validateStep`) ajustada de `.trim()` para checagem direta do valor; a etapa de Revisão ganhou uma linha "Modalidade do plano do dependente" (só quando `mesmoPlano === "nao"`). Este componente é compartilhado — a mudança vale automaticamente para os 2 usos existentes: a tela dedicada `/servidor/requerimento/incluir-dependente` (wrapper fino, seção 4) e os blocos "+ Incluir dependente" inline dentro do wizard de Mudança de Plano (também seção 4).
  - `src/routes/servidor.requerimento.novo-plano.tsx`, `StepDependentes` — `DependentData.modalidade` (antes `string`) virou `ModalidadePlano`; o `<input>` de texto livre na seção "Migrar para outro plano diferente" (`currentData.action === "migrar_outro"`, para dependentes **já cadastrados**, não novos) virou o mesmo `<select>` de 2 opções.
- **Quando `mesmoPlano === "sim"` (Inclusão de Dependente) ou `action === "migrar_titular"` (Mudança de Plano), nenhuma pergunta nova foi adicionada** — nesses 2 casos o dependente está entrando no **mesmo** plano do titular por definição, então a modalidade já é a mesma automaticamente; perguntar de novo seria redundante, não "evitar herança automática" (a regra do pedido é sobre planos **diferentes**, onde a herança seria incorreta).
- **Ressalva deliberadamente fora do escopo — duplicação já existente no plano do titular não foi tocada:** `StepNovoPlano` (mesmo arquivo, plano **do titular**, não do dependente) já tem tanto um campo de texto livre "Modalidade do novo plano" quanto um booleano `empresarial` separado (`Switch`, seção 5) — exatamente o padrão de duplicação que o pedido do usuário pede para evitar. Esse campo é do titular, não de "inclusão de dependente com plano diferente", então ficou fora do escopo explícito do pedido ("aplicar essa regra, no mínimo, aos fluxos... de Inclusão de Dependente; Mudança de Plano quando houver inclusão de dependente") — não foi alterado nesta rodada.
- **Persistência:** sem mudança de mecanismo — `IncluirDependenteValue`/`DependentData` continuam sendo gravados exatamente como antes (`novosDependentes`/`dependentsData` dentro de `RequerimentoMudancaPlanoDraft`, via `saveRequerimentoMudancaPlano()`); só o **tipo** do campo `modalidade` mudou de texto livre para a união estruturada.
- **Relação com o Módulo de Pagamento — preparação para uso futuro, sem integração real ainda:** assim como os campos `empresarial` das seções 3 e 5, este dado fica **só capturado e persistido no rascunho do requerimento** — não há hoje nenhuma leitura desse valor pelo Módulo de Pagamento para determinar automaticamente a exigência documental do beneficiário (Fatura Técnica × Boleto/Recibo/Demonstrativo, ver `docs/MODULO_PAGAMENTO.md` seção 6). Ficar estruturado com o mesmo vocabulário é o que torna essa integração futura possível sem tradução de valores — mas a integração em si continua sendo o próximo passo de maior prioridade já registrado (`docs/MODULO_PAGAMENTO.md`, seção 14, item 1), agora com **3 fontes potenciais** de verdade sobre modalidade de plano por beneficiário (cadastro do titular, requerimento de mudança de plano pendente, e agora também o plano do dependente capturado na inclusão) a serem reconciliadas quando essa integração for feita de verdade.
- **Regras respeitadas:** nenhuma validação nova de obrigatoriedade além da que já existia (o campo já era obrigatório como texto livre; continua obrigatório como select); nenhuma tela nova criada; nenhum outro passo dos 2 wizards foi alterado.
- **Arquivos principais:** `src/lib/mock-data.ts` (tipo `ModalidadePlano` extraído/exportado, reaproveitando `modalidadePlanoLabels` já existente); `src/components/IncluirDependenteForm.tsx`; `src/routes/servidor.requerimento.novo-plano.tsx`.
